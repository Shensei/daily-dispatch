Daily Technical Snippet

Memory poisoning — plant one false fact in an agent's memory and every later recall inherits the lie

An agent's memory is a trust store it writes to itself: what it saw, was told, or concluded, saved for next time. That's also its softest attack surface. Memory poisoning is when an adversary gets a false or malicious fact written into that store — via a crafted document, a prompt-injected web page, or a compromised tool — so it's retrieved later as if it were the agent's own trusted recall. The damage compounds: unlike a one-shot jailbreak, a poisoned memory persists across sessions and silently steers every future decision that touches it. Red-team work like AgentPoison shows you can backdoor an agent by corrupting only a handful of memory entries, with a trigger that's near-invisible in normal use.

Learn more

The defence isn't just better filtering on the way in — it's provenance and ownership on everything already stored. If every remembered fact carries who wrote it, when, and from what source, a poisoned entry is one you can trace, quarantine and revoke instead of a permanent, anonymous truth. That's why this week's sandbox-escape and platform-memory stories both point the same way: a recall you can't audit is a recall you can't defend. The Kepler read: URL-addressable, user-owned memory makes every write attributable and inspectable per recall — so the answer to “should I trust this remembered fact” is checkable by construction, not a matter of faith in the vendor's black box.

→ Chen et al., “AgentPoison: Red-teaming LLM Agents via Poisoning Memory or Knowledge Bases”
